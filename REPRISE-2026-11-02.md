# Où en est le catalogue conteneurs, au 2026-11-02

## La décision qui gouverne tout le reste

**On travaille sur la dernière version majeure, installée depuis le dépôt de
l'éditeur, et la version se mesure avant d'écrire.** Posée par Stéphane le
2026-11-01, après le défaut qui a coûté la journée : le socle installait
`docker.io` de Debian 13, soit l'Engine **26.1.5**, quand le dépôt officiel
servait **29.9.2**. Une formation Docker enseignait sur un moteur de trois
versions majeures de retard.

La règle est consignée dans le `CLAUDE.md` global, et la mémoire du projet la
porte sous `derniere-version-majeure`.

## Les neuf épreuves de fin de module

Écrites et attestées le 2026-11-02, sur décision de Stéphane relayée par la
session du site. Chacune porte cinq contrôles de poids égal, un seuil de 75,
quatre indices payants et **une exigence critique qu'aucun total ne compense**.

| Épreuve | Durée | Exigence critique |
| --- | --- | --- |
| `epreuve-mettre-un-service-en-marche` | 30 min | le conteneur témoin détruit ou redémarré |
| `epreuve-relier-deux-conteneurs` | 30 min | un port publié sur la base |
| `epreuve-remettre-trois-conteneurs-en-service` | 45 min | le rapport tronqué |
| `epreuve-livrer-une-premiere-image` | 45 min | le jeton dans une couche |
| `epreuve-fiabiliser-une-stack` | 45 min | le secret dans l'environnement |
| `epreuve-contenir-un-conteneur-gourmand` | 45 min | les résultats antérieurs perdus |
| `epreuve-reprendre-un-hote-docker` | 60 min | un volume nommé perdu |

| `epreuve-reconstruire-une-image-pour-deux-architectures` | 60 min | le jeton dans l'historique |

Trois d'entre elles touchent la machine et non de simples conteneurs : le démon,
systemd, les comptes, le pare-feu. Chacune a été **éprouvée sur un banc avant
d'être écrite**, et leur cleanup rend la machine telle qu'elle l'a trouvée,
vérifié après coup puisque le cycle de validation ne mesure que les images, les
conteneurs et les volumes.

## Les ruptures de Docker 29, toutes mesurées

Aucune ne se devine en lisant les notes de version, et chacune a cassé au moins
un lab.

| Ce qui a changé | Comment ça se manifestait |
| --- | --- |
| `docker push` publie un **index OCI**, pas un manifeste d'image | `KeyError: 'config'`, et un 404 pour un client qui n'accepte que les types manifeste |
| l'`Id` local d'une image est le digest de son **index** | après `docker load` d'une archive, l'identifiant diffère, fatalement |
| `.RootFS.Layers` reste identique de part en part | c'est désormais lui qui prouve l'identité d'une image récupérée |
| `docker image inspect` **omet les clés vides** de `Config` | une image sans entrypoint n'a plus de clé `Entrypoint` : `KeyError` |
| les capabilities ressortent **préfixées** `CAP_` | `['CAP_NET_BIND_SERVICE'] != ['NET_BIND_SERVICE']` |
| la base d'un `FROM` n'entre **plus** dans le magasin du moteur | `docker build` réussit, puis `docker run <base>` dit « No such image » |
| `docker manifest create` refuse un index en entrée | « probe:amd64 is a manifest list » |
| `docker save` écrit une **disposition OCI** | plus de `manifest.json` à la racine, des `blobs/sha256/` |
| le magasin dépend de l'**histoire de la machine** | installation neuve : containerd ; machine mise à niveau : graph drivers |
| **les images pendantes n'existent plus** sur le magasin containerd | trois builds sur le même tag, puis retrait du tag : zéro pendante. Une image sans référence est ramassée aussitôt, et `docker image prune` ne trouve jamais rien |
| **`docker kill` ne déclenche pas la politique de redémarrage** | un conteneur sous `unless-stopped` reste `exited`, compteur à zéro, sur dix lectures en trente secondes. Le moteur le traite comme un arrêt voulu |
| le noyau protège le **PID 1 d'un namespace** contre un signal venu de l'intérieur | `docker exec <id> kill -9 1` est sans effet, SIGKILL compris |
| **`NET_BIND_SERVICE` ne sert à rien** dans un conteneur | le démon y pose `net.ipv4.ip_unprivileged_port_start = 0` : un conteneur sans aucune capability écoute sur le port 80. Le conseil « tout retirer sauf NET_BIND_SERVICE » ne retire rien d'utile |
| **`docker run --platform` n'honore pas la plateforme** si une image locale correspond déjà à la référence | « Image is up to date », puis l'autre architecture s'exécute. Il faut un `docker pull --platform` explicite |
| un **index publié par buildx porte quatre manifestes**, pas deux | les attestations de provenance s'y présentent comme des plateformes `unknown` |
| **`--build-arg` laisse un secret dans l'historique** | deux occurrences mesurées, là où `--mount=type=secret` n'en laisse aucune, ni dans l'historique ni dans les couches |
| l'image **`registry:3.1.2` déclare un `VOLUME`** | chaque conteneur de registre crée un volume anonyme, et `docker rm` sans `-v` le laisse derrière lui |

Et deux ruptures qui ne viennent pas de Docker :

- **registry 3 exige `auth.token.jwks`.** Le `rootcertbundle` ne suffit plus :
  tout jeton est refusé par « token signed by untrusted key with ID », et
  l'identifiant cité est pourtant celui de la clé de ce certificat
  (distribution/distribution#4470). Le `kid` se calcule à la façon de libtrust,
  et un JWKS au mauvais `kid` est refusé sans que le message change d'un mot.
- **PostgreSQL 18 a déplacé son répertoire de données** vers
  `/var/lib/postgresql/18/docker`, et déclare son volume à
  `/var/lib/postgresql`. Monté à l'ancien `/var/lib/postgresql/data`, il
  **refuse de démarrer** : « unused mount/volume ». Le lab affichait « health
  did not recover within 30 seconds », soit une fausse piste de délai pour un
  défaut de configuration. Au bon point de montage, la base est saine en 2,5 s.

## Les cinq angles morts, à retenir

**Les solutions sont chiffrées, donc invisibles à tout `grep`.** Treize
portaient un digest périmé après la mise à niveau. Une solution qui échoue n'est
pas un détail : c'est elle qui prouve que le lab est **résoluble**.

**Un `.pyc` committé masque une chaîne périmée.** Trois traînaient dans des
`fixtures/`, alors que `__pycache__/` est au `.gitignore`. Celui de
`container-arret-transactionnel` portait l'ancien digest python et a fait passer
un orphelin pour « connu du lab ». Les trois sont retirés ; le contrôle ne lit
plus que les fichiers **suivis et textuels**.

**Un fichier de provenance mentait, et il voyage dans la livraison.**
`PROVENANCE.md` du capstone citait trois digests sur trois à l'ancienne valeur,
et masquait lui aussi un orphelin au contrôle.

**Un indice payant peut mener à une commande qui échoue**, et aucun test ne le
détecte. L'indice de coût 20 de `internes-stockage-des-images` envoyait
l'apprenant sur un champ disparu.

**Un seuil ou une version écrits en dur se périment en silence.** Trois cas
mesurés : le plafond de `images-optimiser-la-taille` tombait 3 863 octets SOUS
la bonne écriture, `container-ulimits-et-shm` exigeait la valeur par défaut, et
le test du capstone imposait `psycopg2-binary == 2.9.11` quand Python 3.14
impose la 2.9.13. Les trois mesurent désormais au lieu de réciter.

## Deux contrôles qui ne prouvaient plus rien, et pourquoi

Ils passaient, et c'est le pire des cas.

**La sonde de poussée de `registry-droits-minimaux`.** Elle faisait repousser au
compte en lecture seule l'image qu'il venait de tirer. Tout étant déjà dans le
registre au bit près, le client **n'écrit rien**, ne demande jamais le droit de
pousser, et sort en 0 : le journal du registre ne porte ni PUT, ni POST, ni
PATCH. Elle pousse maintenant un **contenu inédit**, et le refus a lieu.

**Deux des trois réponses de `internes-chaine-dexecution`.** Le parent du shim
vaut 1 et le runtime vaut `runc` : deux constantes que la leçon hébergeant le
lab enseigne et mesure, donc recopiables. Les trois réponses sont maintenant des
PID propres à l'instance, et le contrôle exige que deux d'entre elles
**s'accordent**.

## Comment rejouer

```bash
cd /home/bob/Projets/containers-dsoxlab-training
export PATH="$PWD/.venv/bin:$PATH"
python3 scripts/valider-labs.py            # les 81, environ deux heures
python3 scripts/valider-labs.py --lab <id> # un seul, pour corriger puis revalider
```

**Une seule campagne à la fois** sur cette machine, et **ne rien modifier dans
`labs/` pendant qu'elle tourne** : un lab modifié en cours de route rend un
verdict qui ne porte sur rien. Corriger un lab se fait **avant** une campagne,
et se revérifie **à l'unité** avant de relancer les 81.

**Ne jamais committer un relevé partiel.** Celui qu'un arrêt a laissé mélangeait
trois moteurs, et un relevé hétérogène inscrit de faux verdicts dans le dépôt,
dont le site se sert pour décider ce qu'il affiche.

Un banc de mesure réutilisable vit dans le scratchpad de session : un inventaire
Ansible qui porte `ansible_host`, la clé du catalogue et les groupes
`lab_target`, `lab_publisher` et `lab_reader`. Il permet de jouer un setup ou
une solution sans passer par `dsoxlab run`, qui ouvre une session SSH
interactive. Sans `ansible_host`, plusieurs setups échouent sur une erreur qui
ressemble à un défaut du lab et n'en est pas.
